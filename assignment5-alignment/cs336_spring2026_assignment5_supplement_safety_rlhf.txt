3.1 Zero-Shot MMLU Baseline
Prompting setup. To evaluate zero-shot performance on MMLU, we’ll load the examples and prompt 
the language model to answer the multiple choice question. Since the language model simply outputs free-
form text, it isn’t always trivial to evaluate its outputs.
In this case, naively prompting the language model with our system prompt and an MMLU example 
means that it’ll sometimes output the letter corresponding to the correct answer, the text of the correct 
answer, or even a paraphrased version of the correct answer. These variations can make it complex to 
parse the answer from the model’s generations.

prompt. In the case of MMLU, we’ll use the following task prompt from cs336_alignment/

↪ corresponding to the correct answer (i.e., A, B, C or D).

A. {options[0]}
B. {options[1]}
C. {options[2]}
D. {options[3]}
Answer:

4.2.1 Data Loader
Our instruction fine-tuning dataset is a collection of prompt-response pairs. To fine-tune our language 
models on this data, we need to convert these prompt-response pairs to strings. We’ll use the following 
template from Alpaca, provided in cs336_alignment/prompts_safety/alpaca_sft.prompt (note that this 
prompt differs from the zero_shot_system_prompt.prompt we used in the previous section). As before, ↪ 
marks a visual line continuation in the PDF and is not part of the prompt:
Below is an instruction that describes a task. Write a response that appropriately
↪ completes the request.
### Instruction:
{instruction}
### Response:
{response}
We can treat these strings as documents for language modeling and train our models on this data. As 
with other types of data, we concatenate all of these documents into a single sequence of tokens, adding a 
delimiter between them, such as the Llama 3.1 8B end-of-text token.
A data loader turns this sequence of tokens into a stream of batches, where each batch consists of 𝐵 
sequences of length 𝑚, paired with the corresponding next tokens, also of length 𝑚.
In practice, examples are often packed into constant-length sequences, which minimizes padding tokens 
and thus maximizes GPU throughput. To break our sequence of token IDs into chunks of length 𝑚, we’ll 
take consecutive, non-overlapping chunks of size 𝑚, dropping the final chunk if it has fewer than 𝑚 
tokens. For example, given token IDs [0, 1, 2, ..., 9, 10] and desired sequence length 4, potential 
batch inputs would be [[0, 1, 2, 3], [4, 5, 6, 7]]. Iterating over the data loader should return each 
of these inputs exactly once, which constitutes an epoch over the data.

4.2.2 Training Script
Now that we’ve implemented a data loader for our instruction fine-tuning data, we’ll write a training 
script to fine-tune a pre-trained Llama 3.1 8B base model.
Loading the model for fine-tuning. Use Hugging Face transformers. We’ll load the model in 
bfloat16 and use FlashAttention-2 to save memory:
from transformers import AutoModelForCausalLM, AutoTokenizer
tokenizer = AutoTokenizer.from_pretrained(model_name_or_path)
model = AutoModelForCausalLM.from_pretrained(
    model_name_or_path,
    torch_dtype=torch.bfloat16,
    attn_implementation="flash_attention_2",
)
Computing language modeling loss. After loading the model, run a forward pass on a batch of input 
IDs and get logits via the .logits attribute. Then compute the loss between the model’s predicted logits 
and labels:
input_ids = train_batch["input_ids"].to(device)
labels = train_batch["labels"].to(device)
logits = model(input_ids).logits
loss = F.cross_entropy(..., ...)
Saving the trained model. Save the model to a directory with save_pretrained. We recommend saving 
the tokenizer as well, even if you did not modify it, so the model and tokenizer are self-contained and 
loadable from a single directory:
model.save_pretrained(save_directory=output_dir)
tokenizer.save_pretrained(save_directory=output_dir)
Gradient accumulation. Despite loading the model in bfloat16 and using FlashAttention-2, even a 
large GPU may not support the effective batch size you want. With the setup above, you should be able 
to train on sequences of 512 tokens with a small per-device batch size. However, we prefer to use a larger 
effective batch size, such as 32 sequences per gradient step.
Gradient accumulation accomplishes this by accumulating gradients over several microbatches before 
taking an optimizer step. Intuitively, if we had a larger GPU, we should get the same result from 
computing the gradient on a batch of 32 examples all at once versus splitting them into 16 batches of 2 
examples each and averaging at the end.
Normally, we run a forward pass, call loss.backward(), call optimizer.step(), and then zero the 
gradients:
10

===== PAGE 11 =====
for inputs, labels in data_loader:
    logits = model(inputs)
    loss = loss_fn(logits, labels)
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
To implement gradient accumulation, call optimizer.step() and optimizer.zero_grad() every 𝑘 steps, 
where 𝑘 is the number of gradient accumulation steps. Divide the loss by gradient_accumulation_steps 
before calling loss.backward() so the gradients are averaged:
gradient_accumulation_steps = 4
for idx, (inputs, labels) in enumerate(data_loader):
    logits = model(inputs)
    loss = loss_fn(logits, labels) / gradient_accumulation_steps
    loss.backward()
    if (idx + 1) % gradient_accumulation_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
As a result, the effective batch size is multiplied by 𝑘.

6 “Reinforcement Learning” From “Human Feedback”
During SFT, we train our model to imitate responses from a given set of high-quality examples. Still, that 
is often not enough to mitigate undesired behavior learned during pretraining. While SFT relies on an 
external set of good examples, for aligning language models it is often helpful to elicit responses from the 
model itself that we are trying to improve, and reward or penalize those responses based on some 
assessment of their quality and appropriateness.
A method that gained popularity recently for its use in the OpenAI models was Reinforcement Learning 
from Human Feedback, or RLHF [L. Ouyang et al., 2022]. In RLHF, we start with a set of prompts to be 
given to our model after SFT. Then, we elicit sets of responses from the model to each prompt. The 
14

===== PAGE 15 =====
“Reinforcement Learning” part of RLHF comes from the fact that we do not get a per-token loss, as we 
have in SFT, since in that setting we are given a reference response. Instead, we train the model to 
optimize for a scalar reward signal that measures how appropriate a complete response is for a given 
prompt. The “HF” indicates that, at least in the original method, this reward signal was obtained from 
fitting a model on data from human annotators, who manually ranked the given sets of responses.
The original RLHF method is fairly intricate. After SFT, we first generate 𝐾 responses for each prompt 
and have humans rank them, which is expensive to do at scale. Then, RLHF proposes to explicitly fit a 
reward model 𝑟𝜃(𝑥,𝑦), which assigns a scalar reward for a response 𝑦 given prompt 𝑥. Here, 𝑟𝜃 starts as the 
SFT model with the final output layer removed and an extra layer that outputs a scalar value. Then, 
sample prompts 𝑥 and pairs of responses 𝑦𝑤, 𝑦𝑙 from the human preferences dataset, where 𝑦𝑤 was ranked 
better than 𝑦𝑙, and optimize:
ℓ𝑟
𝜃(𝑥,𝑦 𝑤,𝑦 𝑙)= − log 𝜎(𝑟𝜃(𝑥,𝑦 𝑤)− 𝑟𝜃(𝑥,𝑦 𝑙)). (1)
Intuitively, we want the reward model to output scalar rewards that agree with rankings from human 
annotators. This loss is lower when there is higher agreement between the reward model and the human 
data.
After fitting a reward model, RLHF proceeds by optimizing the LM using RL, where the LM is a policy 
𝜋𝜃 that receives a prompt and chooses a token to generate at each step until it finishes its response. At 
that point it receives a reward from 𝑟𝜃. The original paper used Proximal Policy Optimization (PPO) for 
training the LM using the reward model. The paper describing RLHF on GPT-3 models also found it 
important to add a KL-divergence penalty to prevent the model from deviating too much from the SFT 
model and to include an auxiliary pretraining language-modeling objective to avoid degenerating 
downstream performance.
RLHF has many moving parts, and has reportedly been difficult to reproduce beyond the success that 
OpenAI had applying it. More recently, another method for aligning models with preference data, Direct 
Preference Optimization (DPO; [R. Rafailov et al., 2023]), has become widely popular for both its 
simplicity and effectiveness, producing models that often perform on par with or better than models 
trained with RLHF. In the last part of this assignment, you will implement DPO and experiment with 
using it to align models using preference labels.
6.1 The DPO Objective
In RLHF, we first explicitly fit a reward model 𝑟𝜃 using collected preference data, and then optimize the 
LM to generate completions that receive high reward. DPO starts from the observation that instead of 
first finding an optimal reward model 𝑟 and then finding an optimal policy 𝜋𝑟 for that reward model, we 
can derive a reparameterization of the optimal reward model represented in terms of the optimal policy 
itself:
𝑟(𝑥, 𝑦)= 𝛽 log(
𝜋𝑟(𝑦 | 𝑥)
𝜋ref(𝑦 | 𝑥)
) + 𝛽 log 𝑍(𝑥). (2)
Here, 𝜋ref is the reference policy: the original LM after SFT that we do not want to deviate too much 
from. The parameter 𝛽 controls the strength of the penalty for deviating from 𝜋ref. The policy 𝜋𝑟 is the 
optimal policy for reward model 𝑟. The second term only depends on an instruction-dependent 
normalization constant 𝑍(𝑥), not on completion 𝑦.
The original per-instance reward-model loss in Equation  1 only depends on differences between rewards 
assigned to different completions. When we take the difference, the partition function cancels out, giving 
the simpler per-instance DPO loss:
15

===== PAGE 16 =====
ℓDPO(𝜋𝜃,𝜋ref,𝑥,𝑦 𝑤,𝑦 𝑙)= − log 𝜎(𝛽 log(
𝜋𝜃(𝑦 𝑤 | 𝑥)
𝜋ref(𝑦 𝑤 | 𝑥)
) − 𝛽 log(
𝜋𝜃(𝑦 𝑙 | 𝑥)
𝜋ref(𝑦 𝑙 | 𝑥)
)). (3)
To compute this loss, we do not need to sample completions during the alignment process as in RLHF. 
All we need is to compute conditional log-probabilities. Thus, there is no explicit reinforcement learning 
happening. The preference data need not necessarily come from human annotators either: several works 
have had success applying these methods on preferences generated by other language models, often 
prompted to judge pairs of alternative responses to the same query.

6.4 DPO Training
You will now implement a training loop using DPO on the HH data. Unlike during SFT, we now have to 
run two examples through the LMs, 𝜋ref and 𝜋𝜃, to compute the loss, which takes significant GPU 
memory. Thus, we will not try to batch our implementation, and will use gradient accumulation, as done 
in SFT, to allow for larger effective batch sizes. Similarly, we won’t use AdamW unless we use other 
efficiency tricks such as quantization, so we will stick to RMSprop, as also done in the original DPO work. 
We suggest the following implementation path, which sacrifices maximal performance for simplicity:
1. Use 2 GPUs, one for the reference model and one for the trained model.
2. Load two copies of your instruction fine-tuned model, one on each device.
3. Separate out a small number of examples, such as 200, as a validation set.
4. Train your model with DPO loss and gradient accumulation, tracking your loss at each step.
5. Start with effective batch size 64, 𝛽 = 0.1, and learning rate 1e-6.
Besides these tricks, keep track of the “classification accuracy” of the implicit reward model on the 
validation set. This simply amounts to comparing the log-probability of chosen and rejected completions, 
considering an example correctly classified when the chosen completion has higher log-probability.
